Kernidee

Ein Dokument ist in Phoedox nur eine Sicht auf Daten. Darunter liegt ein typisierter Graph aus Entitäten (Router, Raum, Endpunkt, Steckdose, Service) und Kanten (hängt an, steht in, wird versorgt von, dokumentiert). Ein Markdown-Text, ein Grundriss und eine 3D-Ansicht zeigen dieselben Entitäten auf unterschiedliche Weise.

Daraus folgt alles Weitere: Die KI fragt den Graphen statt Volltext. Die Fehlersuche läuft einen Pfad ab, statt Seiten zu lesen. Neue Doku-Typen bringen eigene Ansichten mit, nutzen aber denselben Graphen.

Ein Graph

Alle Doku-Typen schreiben in dasselbe Netz. Erwähnt ein Markdown-Text den Router, entsteht eine Kante.

Typen als Plugins

Jeder Doku-Typ ist ein Paket aus Go-Modul, JSON-Schema und Lit-Komponente.

MCP zuerst

Jede Aktion in der UI ist auch ein MCP-Tool. Die UI ist ein Client unter mehreren.

Jeder Eintrag kann eigene Dokumente haben (Kante documents): der Router seine Konfigurationsnotizen, der NAS seine Dienste samt testbaren Requests. Die Geräte-Doku ist ein ganz normales Dokument eines beliebigen Typs.

Jede Kante speichert ihre Quelle (manuell, aus Text erkannt, aus HA importiert, von KI vorgeschlagen). Vorschläge der KI landen als „unbestätigt“ im Graphen, bis jemand sie annimmt.

Doku-Typen als Plugins

Markdown und Grundriss sind die ersten Typen, nicht die einzigen. Ein Typ wird über ein Manifest registriert und liefert vier Dinge:

// Go, Backend-Seite eines Doku-Typs
type DocType interface {
    ID() string                         // "floorplan"
    Schema() json.RawMessage            // JSON-Schema des Inhalts
    Validate(doc *Document) error
    Extract(doc *Document) []GraphOp    // Entitäten + Kanten ins Netz schreiben
    Tools() []mcp.Tool                  // eigene MCP-Tools, z. B. place_device
}
// Frontend: <phx-doc-floorplan> als Lit-Element, per dynamic import geladen

Doku-Typ Komponente

  • Quellen: Dateien wie in einem kleinen Projekt (z. B. Button.tsx, button.css) plus phoedox.component.json mit Props, Aktionen, Ereignissen und Varianten.
  • Bauen: esbuild läuft als Go-Bibliothek im Server und baut beim Speichern ein ES-Modul. Frameworks über Adapter: React, Vue, Svelte, Lit, reines HTML/CSS/JS. Pakete nur aus Allowlist oder eigenem Registry-Spiegel, Ergebnis gecacht.
  • Anzeigen: in einem Sandbox-iframe auf eigener Herkunft (sandbox.<instanz>), damit fremder Code nicht an Sitzung oder Daten kommt. Kommunikation über postMessage.
  • Steuerung: aus dem Manifest entstehen Eingaben je Typ (Text, Zahl, Bereich, Auswahl, Farbe, Ja/Nein). Platz wählbar: rechts neben der Vorschau oder darunter. Aktionen rufen Methoden der Komponente auf (z. B. Animation starten), Ereignisse erscheinen im Protokoll.
  • Varianten sind gespeicherte Prop-Sätze. Viewports (Mobil, Tablet, Voll) und heller/dunkler Hintergrund zum Prüfen.
  • Einbetten: per / in jedem Markdown-Dokument mit festen Props; die Kante embeds zeigt, wo eine Komponente benutzt wird.
  • KI: MCP-Tools component.describe und component.render (Bild mit beliebigen Props).

Doku-Typ Datenbankmodell

  • Ansicht: ER-Diagramm mit Tabellen, Spalten, Typen, Pflichtfeldern, Primär- und Fremdschlüsseln (mit ON DELETE-Regel), Indizes und Kardinalität an den Linien; daneben eine Tabellenansicht. Layout automatisch, Positionen per Hand verschiebbar und live für alle (Yjs).
  • Quellen: SQL-DDL einfügen, Migrationen importieren (goose, Flyway, Prisma, Django, Rails) oder live auslesen über den Agenten (Postgres, MySQL/MariaDB, SQLite, SQL Server; nur Schema, keine Daten).
  • Versionen: jeder Import ist eine Version. Zwei Versionen lassen sich vergleichen (neue, geänderte, gelöschte Tabellen und Spalten farbig); aus dem Vergleich entsteht auf Wunsch ein Migrationsskript. Die Live-Datenbank kann gegen die dokumentierte Version geprüft werden („Abweichung seit 3 Tagen“).
  • Im Netz: jede Tabelle ist ein Eintrag mit eigener Doku. Dienste hängen per used_by daran, die KI beantwortet z. B. „Welche Dienste schreiben in orders?“. Spalten können als personenbezogen markiert werden.
  • Export: DDL, Markdown-Tabellen, PNG/SVG des Diagramms; Einbetten einzelner Tabellen in Markdown.

Request-Blöcke laufen über das Go-Backend (nicht im Browser), damit es kein CORS-Problem gibt und Geheimnisse in einer Projekt-Umgebung ({{baseUrl}}, {{token}}) bleiben, die nie im Dokument steht.

Architektur

  • Ein Go-Binary mit klaren Modulen, Frontend per embed ausgeliefert. Einfach selbst zu hosten.
  • Postgres mit Tabellen entities und edges, Attribute als JSONB. Pfadabfragen per rekursivem CTE, das reicht für Haushalt und mittlere IT-Landschaften. Eine echte Graph-DB ist erst bei Bedarf nötig.
  • Event-Log für jede Änderung (wer, was, über UI oder MCP). Daraus kommen Verlauf, Live-Updates per SSE und das Neuberechnen von Index und Kontextpaketen.
  • Frontend: Lit-Komponenten, Vite als Bundler, Bun als Paketmanager und Test-Runner. 3D über three.js nur im Typ house3d nachgeladen.

Wissensnetz für KI

Damit eine KI schnell an die richtige Information kommt, arbeitet der Index auf drei Ebenen:

1 · Struktur

Graph-Abfragen: „alles im Arbeitszimmer“, „Pfad vom Laptop zum Internet“. Exakt und billig.

2 · Bedeutung

Embeddings pro Block und Entität, Volltext daneben. Für unscharfe Fragen.

3 · Kontextpakete

Pro Entität vorberechnete Kurzfassung mit Nachbarn, Status und Quellen. Wird bei Änderungen neu gebaut.

Eine Antwort beginnt mit einer Suche, springt dann über Kanten zu den Nachbarn und liefert das Kontextpaket. So braucht die KI meist einen oder zwei Tool-Aufrufe statt zehn.

MCP-Schnittstelle

Der MCP-Server läuft im Go-Binary, Authentifizierung per OAuth bzw. persönlichem Token. Er sieht genau die Projekte, die der Nutzer sieht. Grundwerkzeuge:

ToolZweck

Home Assistant

  • Jeder Nutzer verbindet seine eigene HA-Instanz (URL + Long-Lived Token, verschlüsselt gespeichert). Live-Status kommt über die HA-WebSocket-API.
  • Eine Phoedox-Entität bekommt ein Binding auf eine HA-entity_id. Ein Router mit powered_by zu einem Smart-Plug erhält dadurch automatisch die Aktion „Neu starten (Strom aus, 10 s, an)“.
  • Teilt jemand ein Projekt, sehen andere die Doku, aber nicht die Steuerung, außer sie haben selbst Zugriff auf dieselbe HA-Instanz oder bekommen das Recht „steuern“.
  • Schaltaktionen über MCP verlangen eine Bestätigung in der UI oder eine vorher erteilte Freigabe pro Gerät. Ein abgeschalteter Router trennt sonst auch die KI selbst.

Projekte & Rechte

Jedes Projekt hat eine Primärfarbe (Standard: Phoedox-Orange). Phoedox leitet daraus eine helle und eine dunkle Variante ab, die auf Weiß bzw. Dunkel mindestens 4,5:1 Kontrast haben, plus eine zarte Flächenfarbe. Die Farbe gilt in der App, sobald das Projekt offen ist, und in Veröffentlichungen pro Projekt: Wer im Projekt-Menü wechselt, sieht die Farbe des jeweiligen Projekts. Ändern dürfen sie Besitzer des Projekts.

Ein Projekt ist der Rahmen für Dokumente, Graph und Umgebungsvariablen: „Wohnung Lindenstraße“, „Kunden-ERP“, „Homelab“. Rollen: Besitzer, Bearbeiter, Leser, dazu das Zusatzrecht Steuern. Entitäten können projektübergreifend verlinkt werden (der Homelab-Server steht im Keller der Wohnung), sichtbar ist die Kante nur für Leute mit Zugriff auf beide Seiten.

Veröffentlichungen

Eine Veröffentlichung ist ein eigenes Objekt neben den Projekten. Sie verweist auf ein oder mehrere Projekte, legt Reihenfolge, ausgewählte Seiten, Zugriff und Domain fest. So lassen sich z. B. Handbuch, API und Plugin-SDK als docs.phoedox.com zusammenfassen.

Was öffentlich wird

  • Nur ausdrücklich gewählte Seiten. Seiten mit Verweisen auf Geheimnisse ({{…}} aus der Projekt-Umgebung) sind gesperrt.
  • Home-Assistant-Werte, Schalter, Präsenz und Verlauf erscheinen nie.
  • Erwähnungen von nicht veröffentlichten Einträgen werden zu normalem Text, damit keine internen Namen verlinkt werden.
  • Request-Blöcke können Besucher mit ihrem eigenen Token ausprobieren; die Umgebungen des Projekts bleiben privat.

Zugriff und Stand

  • Zugriff: öffentlich, mit Passwort oder nur für angemeldete Nutzer (Konten der Instanz, OIDC-Gruppen).
  • Stand: immer aktuell oder nur freigegebene Versionen. Versionen sind feste Schnappschüsse, alte bleiben unter /v/12/… erreichbar.
  • Eigener Suchindex und optional ein öffentlicher, nur lesender MCP-Endpunkt plus llms.txt, damit auch fremde KIs die Doku gut lesen.

Eigene Domain

  • Standard: <name>.phoedox.site. Eigene Domain per CNAME auf sites.phoedox.com plus TXT-Eintrag _phoedox.<sub> als Nachweis.
  • TLS über ACME (Let’s Encrypt) mit CertMagic in Go, „on demand“ nur für bestätigte Domains. Verlängerung automatisch.
  • Der Go-Server erkennt am Host-Header, welche Veröffentlichung gemeint ist, und rendert sie serverseitig. Seiten werden gecacht und bei Änderungen gezielt neu gebaut.
  • Selbst gehostet funktioniert es genauso, der CNAME zeigt dann auf die eigene Instanz.

Navigation der öffentlichen Seite

Jedes Projekt hat eigene Kategorien und Überschriften. Deshalb zeigt die Seitenleiste immer nur ein Projekt. Gewechselt wird über ein Projekt-Menü oben in der Seitenleiste, ab fünf Projekten mit Suche, wie die Projektauswahl in der App. Die Suche der Seite durchsucht alle Projekte und zeigt das Projekt am Treffer.

Organisationen & Lizenzen

Aufbau: Instanz → Organisationen → Projekte. Nutzer können mehreren Organisationen angehören und zusätzlich einen persönlichen Bereich haben.

RolleDarf
System-AdminInstanz-Domains, Zertifikate, Plugins installieren, Organisationen anlegen und ihre Nutzungsart festlegen (kommerziell / nicht-kommerziell), eigene App-Domains pro Organisation erlauben und begrenzen
Org-AdminMitglieder und Rollen, eigene App-Domains (z. B. docs-intern.firma.de), Anmeldung/OIDC der Organisation, Plugins für die Organisation einschalten und Lizenzen kaufen
MitgliedProjekte nach Projektrolle (Besitzer, Bearbeiter, Leser, Steuern)

Eigene App-Domains

  • CNAME auf die App-Domain der Instanz plus TXT-Eintrag als Nachweis. Zertifikat wie bei Veröffentlichungen automatisch.
  • Der Server erkennt am Host-Header die Organisation: eigene Anmeldeseite mit Logo, eigener OIDC-Anbieter, Start direkt in den Projekten der Organisation.
  • Cookies gelten pro Host. MCP und OIDC-Rückleitungen gibt es pro Domain.
  • In Phoedox Cloud funktioniert es genauso; der System-Admin ist dort der Betreiber.

Plugin-Lizenzen

  • Anbieter wählen im Manifest: kostenlos, privat kostenlos, kommerziell kostenpflichtig oder kostenpflichtig.
  • Die Nutzungsart der Organisation entscheidet, ob gezahlt werden muss. Persönliche Bereiche gelten als nicht-kommerziell.
  • Kommerzielle Organisationen bekommen eine Probezeit (z. B. 14 Tage). Danach bleibt das Plugin lesbar, aber Schreiben und MCP-Tools sind gesperrt.
  • Lizenzen kauft der Org-Admin im Store; sie sind an Instanz-ID und Organisation gebunden und liegen als signierte Datei vor, auch offline gültig.
  • Bei Self-Hosting setzt der eigene System-Admin die Nutzungsart. Das beruht auf den Lizenzbedingungen des Plugins; der Store kann bei Verdacht nachfragen, technisch erzwingen lässt es sich nicht.

Plugin-Store

Plugins kommen aus einem eigenen Store (eigene Plattform, ähnlich JetBrains Marketplace). Eine Instanz installiert sie zur Laufzeit, ohne neu gebaut zu werden.

Paketformat

phoedox-plugin.json
{
  "id": "de.example.rack-view",
  "version": "2.3.0",
  "engines": { "phoedox": ">=1.4.0 <2.0.0" },
  "doctypes": ["rack"],
  "permissions": ["graph:read", "graph:write", "net:fetch:*.example.com"],
  "backend": "backend.wasm",        // Go-Seite, läuft in wazero
  "frontend": "frontend/index.js",  // Lit-Komponenten als ES-Modul
  "mcpTools": ["rack.place_device"]
}
  • Backend als WebAssembly (in Go mit wazero ausgeführt): Plugins laufen isoliert, sprechen nur über eine definierte Host-API mit Graph, Dateien und Netz und bekommen nur die Rechte aus ihrem Manifest. Dritte können in Go (TinyGo), Rust oder anderen WASM-Sprachen schreiben.
  • Frontend als ES-Modul, das Web Components registriert. Es wird dynamisch geladen und sieht nur ein Plugin-SDK, nicht die Interna der App.
  • Signiert: Der Store signiert jede Version, die Instanz prüft die Signatur vor der Installation.

Versionen und Kompatibilität

Jede hochgeladene Version gibt im Feld engines.phoedox an, mit welchen Phoedox-Versionen sie läuft. Die Instanz schickt beim Abruf ihre eigene Version mit. Der Store liefert dann die neueste kompatible Plugin-Version, nicht einfach die neueste.

Plugin-Versionengines.phoedoxInstanz 1.6Instanz 2.1
2.3.0>=2.0 <3.0–installiert
2.2.1>=1.4 <2.0installiert–
2.0.0>=1.2 <2.0älter–
  • Nach einem Phoedox-Update prüft die Instanz alle Plugins und bietet passende neue Versionen an. Ein Plugin ohne kompatible Version wird deaktiviert, die Daten bleiben erhalten.
  • Plugins bringen Migrationen für ihre Inhalte mit (Schema-Version im Dokument), damit Updates bestehende Dokumente umbauen können.
  • Instanzen ohne Internet laden Pakete als Datei hoch. Firmen können einen eigenen Store-Spiegel betreiben (gleiche API).
  • Store-Funktionen: Verlag-Konten, Upload per CLI/CI, Kanäle (stable / beta), Changelog, Download-Zahlen.
  • Später: kostenpflichtige Plugins mit Lizenzprüfung durch den Host (signierte Lizenzdatei, auch offline).

Plugin-Host-API

Ein Plugin besteht aus zwei Teilen: einem Backend-Modul (WebAssembly), das im Go-Server isoliert läuft, und einem Frontend-Modul (ES-Modul mit Lit-Komponenten), das im Browser geladen wird. Beide sprechen nur über definierte Schnittstellen mit Phoedox. Ein Plugin sieht nie mehr als der Nutzer, in dessen Namen es gerade läuft.

Laufzeit

Empfehlung: Extism auf Basis von wazero. wazero ist eine WebAssembly-Laufzeit in reinem Go ohne CGO, das passt zum einen Binary. Extism liefert darüber fertige Speicherverwaltung, Host-Funktionen und PDKs für Go (TinyGo), Rust, AssemblyScript, Zig, C und weitere. Plugin-Autoren nutzen ein dünnes phoedox-pdk pro Sprache, das die Rohaufrufe in typisierte Funktionen verpackt.

  • Datenformat zwischen Host und Plugin: JSON in Version 1. Später optional MessagePack für große Grundrisse.
  • Jeder Aufruf bekommt einen Kontext: Nutzer, Projekt, Instanz-Version, Locale, Anfrage-ID.
  • Instanzen werden pro Plugin vorgeladen und wiederverwendet; der Zustand zwischen Aufrufen lebt im kv-Speicher, nicht im WASM-Speicher.

Frontend-SDK

Das Frontend-Modul registriert Web Components und meldet sie beim SDK an. Es bekommt die Design-Tokens als CSS-Variablen und darf nur über das SDK mit dem Server reden.

import { definePlugin, html, css, PhxElement } from "@phoedox/sdk";

class UpsBlock extends PhxElement {
  static properties = { entity: { type: String }, state: { state: true } };
  static styles = css`.v { font-family: var(--phx-font-mono); color: var(--phx-fg); }`;
  async connectedCallback() {
    super.connectedCallback();
    this.sdk.graph.watch(this.entity, e => (this.state = e.attrs)); // live über SSE
  }
  render() {
    if (!this.state) return html`…`;
    return html`<span class="v">${this.state.ladung} % · ${this.state.laufzeit} min</span>`;
  }
}

export default definePlugin({
  elements: { "phx-ups-block": UpsBlock },
  blocks: [{ id: "ups-status", element: "phx-ups-block", icon: "battery-charging" }],
});

Das SDK bietet sdk.graph, sdk.docs, sdk.tool() (eigene MCP-Tools aufrufen), sdk.ui (Toast, Dialog, Seitenleiste), sdk.realtime (Zugriff auf das CRDT des Blocks) und sdk.icons (Lucide-Namen).

Beispiel: Backend in Go

package main

import pdk "github.com/phoedox/pdk-go" // baut auf extism/go-pdk auf

// Wird laut Manifest alle 60 s aufgerufen.
//go:wasmexport on_event
func onEvent() int32 {
    pass, _ := pdk.Secret("nut_password")
    res, err := pdk.Fetch(pdk.Request{
        URL:     "https://nut.lan/api/v1/ups/usv-keller",
        Headers: map[string]string{"Authorization": "Bearer " + pass},
    })
    if err != nil {
        pdk.Log.Warn("USV nicht erreichbar", err)
        return 0
    }
    var st struct{ Charge, Runtime int }
    res.JSON(&st)

    ups, _ := pdk.Graph.FindOne("ups", pdk.Where{"name": "USV Keller"})
    pdk.Graph.Upsert("ups", ups.ID, map[string]any{
        "ladung": st.Charge, "laufzeit": st.Runtime / 60,
    })
    return 0
}

Versionierung

  • hostApi ist eine eigene Hauptversion. Eine Phoedox-Version unterstützt immer die aktuelle und die vorige (z. B. 2 und 1), damit Plugins Zeit für Updates haben.
  • Neue Host-Funktionen kommen ohne neue Hauptversion dazu; ein Plugin fragt mit host.has("ha.history") nach.
  • Der Store nutzt engines.phoedox und hostApi, um die neueste kompatible Version auszuwählen.
  • Später: kostenpflichtige Plugins. Die Lizenz prüft der Host, nicht das Plugin; Instanzen ohne Internet bekommen eine signierte Lizenzdatei.

Werkzeuge für Plugin-Autoren

  • phx plugin new legt ein Gerüst für Go oder Rust mit Lit-Frontend an.
  • phx plugin dev verbindet sich mit einer lokalen Instanz und lädt Backend und Frontend bei jeder Änderung neu.
  • phx plugin test startet einen simulierten Host mit Beispielgraph, prüft Rechte und Grenzen.
  • phx plugin publish signiert und lädt die Version in den Store, auch aus CI.
